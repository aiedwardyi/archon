═══════════════════════════════════════
STRUCTURAL REQUIREMENTS (NON-NEGOTIABLE)
═══════════════════════════════════════

1. DARK THEME — NON-NEGOTIABLE. Background #0d1117, sidebar #161b22, cards #1c2128.
- This archetype is a broad analytics / operations dashboard, not a live trading terminal.
- Avoid crypto exchange branding, ticker rows, trade buttons on every row, candlestick language, or market-terminal motifs unless the user explicitly asked for a finance product.

2. SIDEBAR — 220px fixed left. NEVER collapsible. Contains:
   - .sidebar-logo (icon + app name, 60px height)
   - .sidebar-nav with 2 .sidebar-group sections (e.g. "PLATFORM" and "SYSTEM")
   - 6-8 .sidebar-item entries with SVG icons (18x18px). One has .active class.
   - .sidebar-user at bottom (avatar + name + email)

3. HEADER BAR — .header-bar (60px, sticky top). Contains:
   - .page-title (e.g. "Revenue Pulse", "Dispatch Command Center", or another domain-specific title that fits the chosen product)
   - .header-actions: .header-search (search icon + placeholder text), .header-icon-btn (bell icon for notifications), .header-avatar
- The page title and labels should read like analytics, platform health, customer success, operations, or portfolio management, not like a brokerage trading screen.
- Avoid generic dense-shell titles like `Dashboard Overview`, `Analytics Dashboard`, or `Portfolio Overview` unless the user explicitly asked for that exact wording.
- Use the provided display font for the brand, page title, and section titles. Use the mono family for KPI values, deltas, table numerics, timestamps, and chart labels.

4. MAIN CONTENT — .main-content > .content-area

═══════════════════════════════════════
REQUIRED SECTIONS (inside .content-area)
═══════════════════════════════════════

1. KPI CARDS — .kpi-grid with exactly 4 .kpi-card:
   - Each: .kpi-label, .kpi-value (large number), .kpi-delta (up/down with arrow + percentage)
   - Values MUST be realistic, positive, and varied (e.g., ARR, active accounts, completion rate, avg. response time, total managed value, projects shipped). Ensure they represent meaningful, actionable metrics for a broad dashboard rather than only market prices.
   - ZERO-VALUE BAN: never "0", "$0", "0%" – all values must be non-zero and convey active, dynamic data.
   - Use .kpi-delta--up for positive, .kpi-delta--down for negative
   - One .kpi-card MUST be visually distinct with an elevated treatment (e.g., using .card-elevated from base.css, or custom layered shadows) to highlight a primary metric.

2. CHART — .chart-card (has accent top border) with .chart-header (.chart-title + period buttons):
   - .chart-header: display:flex between .chart-title and a div of .chart-period-btn buttons
   - Period buttons: 4x .chart-period-btn (1D, 1W, 1M, 1Y). "1M" gets .active class (green bg)
   - SVG line chart with 12+ data points (monthly data, Jan-Dec)
   - Chart data should depict a clear, plausible trend (e.g., growth, fluctuation) over the period, not just random points.
   - Chart SVG: visible path with stroke var(--accent), stroke-width 2, fill below with linearGradient (accent 10% opacity to transparent)
   - Y-axis labels: 5 labels at left edge, font-size 12px, color var(--text-secondary) — MUST be readable
   - X-axis labels: month abbreviations, font-size 11px, color var(--text-muted)
   - Horizontal grid lines: stroke rgba(255,255,255,0.04), 5 lines
   - Add small circle dots (r=3, fill accent) on 3-4 data points for emphasis
   - Implement a simple, non-intrusive tooltip on hover over data points, displaying the exact value and date/month.
   - NEVER leave chart empty — must have real SVG path data
   - Add at least 2 contextual action chips (e.g. "Rebalance", "Export CSV") using `.interactive-chip` with visible hover states
   - At least 1 chart action chip must do something visible on click: toggle a comparison series, reveal a compact insight panel, open an export drawer, or switch a summary state. Dead chips are a failure.

3. HOLDINGS TABLE — .data-table-wrapper > .data-table:
   - thead: 6 columns (Name, Price, 24h Change, Holdings, Value, Action)
   - Add a subtle visual separator (e.g., a thin border-bottom) to the `<thead>` for clear distinction from `<tbody>`.
   - tbody: 8+ rows with realistic data
   - .cell-primary for asset names
   - .cell-positive / .cell-negative for price changes (include + or - prefix)
   - Action column: use context-appropriate actions like "Review SLA", "Inspect Route", "Escalate", "Approve", or "Open Case". Do not default to "Trade" unless the user's prompt is explicitly financial trading.
   - Avoid repeating the same generic `View` / `Details` verb across the whole table. Row actions should reflect the actual workflow.
   - font-variant-numeric: tabular-nums on all numbers
   - NEVER use double currency symbols ($$)
   - At least 1 visible action in the table must open a meaningful inline detail state, drawer, or modal with local mock data. Do not ship inert row actions.

4. ACTIVITY FEED — .activity-feed with .feed-header + 5-6 .activity-item entries:
   - Each: .activity-icon (colored circle with icon), .activity-text (with <strong> for emphasis), .activity-time
   - Timestamps: "2 min ago", "15 min ago", "1 hour ago" etc.
   - Mix of .activity-icon--buy, --sell, --info

Use .grid-2col to arrange chart + activity feed side by side, or table + activity feed.
- Prefer one non-market secondary module such as alerts, team activity, customer health, operational incidents, or project delivery status to keep the dashboard distinct from fintech.
- The desktop right rail should not feel empty. Stack at least two subsections or give the feed an internal split (for example alerts + activity, customers at risk + deployments, or incidents + approvals) so the secondary column carries real visual weight.
- The right rail must carry visible interaction, not just passive text. Include at least one compact approval row, alert card, or incident item with an actionable control that changes state when clicked.
- Do not leave the support rail labeled only as plain `Watchlist`, `Activity Feed`, or `Recent Updates` unless the product is explicitly market/trading and the modules still carry product-specific context.

═══════════════════════════════════════
DATA & CONTENT RULES
═══════════════════════════════════════

- ALL numbers use tabular-nums (set on body in base.css)
- Currency formatting: $XX,XXX.XX — never $$, never missing decimals for prices
- Percentages: include + or - prefix for changes
- Table rows: minimum 8 rows with varied data
- Activity timestamps: realistic, varied ("just now", "5 min ago", "2 hours ago")
- Domain context: adapt accent color in style.css if needed (green for crypto/finance, blue for SaaS analytics)
- Do not add a ticker strip, watchlist, or trading rail unless the user's prompt explicitly asks for a market/trading product.
- Table rows MUST have hover state (background lighten on hover — already in base.css)
- KPI cards hover state: subtle lift + accent border glow (already in base.css)
- Chart period buttons: one must have active/selected state
- Depth polish target: include 1 elevated card treatment using layered shadows (shadow + subtle inner highlight), not flat surfaces only
- Use styled initials, local assets, or inline SVG avatars. Do not use remote placeholder avatar/image services.
- The shell should feel operationally alive: include at least one obvious active/open state, one hover state, and one click-triggered state beyond nav/search.
- Avoid generic “search bar + cards + table + feed” sameness. Vary panel accents, support-module tone, and secondary-rail structure so the dashboard reads as intentionally designed rather than scaffolded.
- Titles, support-rail labels, and row actions should sound authored for the chosen product, not like reusable template filler.
- Tablet/mobile layout must stay composed. Below `1024px` and `768px`, rails must not overlap or clip, sidebars must not create awkward empty gutters, and control clusters should wrap intentionally instead of drifting out of alignment.

═══════════════════════════════════════
LAYOUT STRUCTURE (CRITICAL)
═══════════════════════════════════════

The dashboard MUST fill the full 1440px viewport. Do not let content collapse into a narrow column.
- .dashboard-layout: display flex, sidebar + main-content side by side
- .main-content: margin-left 220px (sidebar width), fills remaining width
- .kpi-grid: 4 columns at desktop (repeat(4, 1fr)) — NEVER collapse to 1 column above 1200px
- .grid-2col: 2fr 1fr at desktop (chart/table takes 2/3, right rail takes 1/3)
- The right rail must sit BESIDE the chart/table, not stacked below
- Do NOT add responsive overrides in style.css that collapse the grid at desktop widths
- If using base.css classes, do NOT redefine their grid-template-columns in style.css
